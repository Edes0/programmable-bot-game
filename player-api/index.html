Programmable bot game · Player API

Write one bot.
Watch it live forever.

You write a single function. The world calls it once per tick, on every creature you own, for as long as your colony survives. This is the reference for what your bot can see and do — the rest is yours to write.

01 What you're writing

The whole contract in one breath.

Your bot is one entry point — a function called play (aliases tick / main). The engine calls it once per tick and hands it a fresh game object: a read-only snapshot of everything you can currently perceive. Inside play you look at the world and issue intents — move this drone, gather here, spawn a new one. Then the tick ends, the engine reconciles everyone's intents into a new world, and calls you again.

def play(game):
    # called every tick, forever. do a little; return.
    for unit in game.units:
        unit.moveTo(unit.x + 1, unit.y)   # drift east
The rhythm is idle, not arcade. A tick is ~1000 ms of wall-clock. Sessions are punctuation; idle is the loop. You drop in to watch your colony glow and drift, adjust the bot, and drop out again. Design for a colony that runs well while you're not looking.
Do a little each tick. Your play has a hard CPU / wall-clock budget. Don't loop forever, don't block on I/O. Look, decide, issue intents, return. Spread heavy work across ticks (e.g. if game.time % 10 == 0:).

02 The tick loop

State in → your code → intents out → a new world.

Two consequences fall out of this loop, and they trip up almost everyone at first:

  • Intents are wishes, not guarantees. You ask to move; the engine resolves collisions, range, and conflicts against every other player, then applies the outcome. Your call returns immediately (True/true) — that means "queued", not "done".
  • Movement is per-tick (see §05). An intent lasts one tick. If you don't re-issue moveTo next tick, the unit stops.

03 The world & coordinates

One continuous plane. Global coordinates. No walls at the edges.

The world is a single flat 2D plane. Every position you read — a unit's, a resource's, a structure's — is a global (x, y) ground coordinate. It does not reset at room boundaries. "Rooms" are only an internal engine partition of the map — your bot is never told which room anything is in. There is no roomName on game, units, or structures, and no room= argument anywhere. You navigate the one continuous plane in global coordinates and the engine handles the seams.

To send a unit anywhere — one step or three rooms away — you name one point and the engine routes across seams for you:

# walk to a resource, wherever it is on the plane
unit.moveTo(resource.position.x, resource.position.y)

# or hand moveTo the object directly
unit.moveTo(resource)

# "go 10 tiles east" — the coordinate never snaps back at a border
unit.moveTo(unit.x + 10, unit.y)
Distance is real. a.distanceTo(b) gives the true Euclidean distance in tiles (not squared), over global (x, y). Both sides can be a Position, a unit, a resource, or a structure — anything with a position.

04 What your bot sees each tick

The game object and the things hanging off it. Everything is a read-only snapshot for this tick.

resource

MemberTypeMeaning
resource.positionPositionWhere the cell is. Read .position.x / .y.
resource.resourcesdictWhat's here: {resourceType: amount}.

resource.pathDistanceint / NoneSteps from your nearest hatchery to this cell — how many ticks of walking it costs, following real terrain rather than cutting through mountains. None means either that you own no hatchery to measure from, or that there is no walkable route to the cell at all — unreachable patches are listed, they just have no distance.
A resource is a cell, keyed by position. resource.id is just its truncated "x,y" coordinate, so it's stable tick-to-tick — the same physical cell always has the same id. Keying on resource.id and keying on the position are the same thing.

position

Memory: game.memory is a plain dict that survives between ticks. Store role assignments, target coordinates, a state machine — anything. Read it at the top of play, mutate it, and the engine saves the changes for you. Keep it modest; it's persisted every tick.

05 What your bot does — intents

Four verbs on a unit, plus spawning. One meaningful intent per unit per tick.

IntentEffect
unit.moveTo(x, y)
unit.moveTo(target)		Step toward a global point (or any positioned object). The engine paths and resolves collisions. Per-tick — re-issue every tick until arrival.
unit.gather(resource)Harvest from a resource cell you're within game.gatherRange of — pass the Resource (or its id). Resolves by identity, mirroring transfer/attack. Fills inventory up to capacity.
unit.transfer(structure)Hand your cargo to a structure within game.transferRange (e.g. deposit mineral into a hatchery).
unit.attack(target)Melee an enemy unit within game.attackRange — pass a game.hostiles entry (or its id). Damage scales with the attacker's surviving ATTACK parts.
structure.spawnUnit(body, unit_type)A hatchery births a new unit — see §06.
Re-issue movement every tick. An intent is consumed by the tick that receives it and remembered no further. If your unit lost a movement conflict this tick, the engine simply dropped that one move — call moveTo again next tick. Code that sets a destination once and waits will sit still forever.
One meaningful intent per unit per tick. Issuing two moves for the same unit in one tick keeps only the last. Structure your loop so each unit decides once.

06 Growing your colony — body composition

A unit is an ordered list of parts. Order is survival order.

A hatchery births a unit from a body: a required, ordered array of part tokens. The parts you choose set the unit's stats; the order sets what dies first.

hatchery = next(s for s in game.structures if s.type == "hatchery")
hatchery.spawnUnit(["TOUGH", "MOVE", "MOVE", "WORK", "CARRY"])

The part menu

TokenCost (mineral)Gives
MOVE50Speed. More surviving MOVE = faster; cargo & weight slow you.
CARRY50Carrying capacity.
WORK100Gather rate.
ATTACK80Melee damage.
RANGED_ATTACK150Ranged damage.
TOUGH10Cheap hit points — expendable front armor.

Spawn cost = the sum of part costs; the hatchery must hold that much mineral. An empty body is rejected.

  • Parts degrade front-first. As a unit takes damage, whole parts are destroyed from index 0 outward — lose front CARRY and capacity drops; lose WORK and you gather slower.
  • Speed reflects MOVE vs. load. A full hauler moves slower than an empty one; a heavy body slower than a light one. A unit with no MOVE still crawls.
  • Designing the body is your craft. The engine carries the array you chose and reports the outcome — read it back any tick via unit.bodyComposition, and watch unit.health fall as parts die. It never picks or orders parts for you.
One birth at a time. A hatchery has a single build slot: spawnUnit opens a gestation timer, and further spawns are rejected until it finishes. This single slot is your spawn rate limit.

07 Fog of war

You see what you can see. The rest is remembered, or dark.

Fog hides what's on the map, never the map itself.

The ground is public. game.terrainAt(x, y) tells you what a cell is — "normal", "mountain" or "lava" — for any cell in the world, whether or not you've ever been there. So "can something of mine stand here?" is always just:

walkable = game.terrainAt(x, y) == "normal"

What fog still hides is everything that moves or changes: enemy units, enemy structures, and how much is actually left in a patch you haven't looked at. That's what visibilityAt is for.

Every reachable resource cell is in game.resources from tick 1. You do not have to explore to find ore — send a miner to the nearest patch on your first tick if you like. A cell you've seen carries its last-known amount and a last-seen tick; a cell you haven't carries the amount the map was generated with and no last-seen tick. So a patch someone else has been draining still reads full to you until you go and look. Cells nothing of yours could ever walk to aren't listed at all.

"Nearest" should mean nearest to walk to. Each cell carries pathDistance: the number of steps from your closest hatchery, following ground a unit can actually stand on. A patch 10 cells away behind a ridge can cost 90 steps, while one 30 cells away across open ground costs 30 — straight-line distance cannot tell those apart, and sorting by it sends miners the long way round. Watch the 0: a patch directly under a hatchery has pathDistance == 0, which is falsy, so compare against None.

# closest patch by walking cost, not by how near it looks
reachable = [r for r in game.resources if r.pathDistance is not None]
target = min(reachable, key=lambda r: r.pathDistance)
for res in game.resources:
    live = game.visibilityAt(res.position.x, res.position.y) == "visible"
    seen = res.last_seen_tick is not None       # False = you've never looked here
    age  = game.time - (res.last_seen_tick or 0)   # how stale, in ticks

Structures you've seen are still remembered when they fog over — they stay in game.structures with their last-known state and a last-seen tick. Units are never remembered (they move).

The world has edges, and they answer as "mountain". Ask terrainAt about a cell outside the world and you get "mountain", because that's what it is to you: somewhere you cannot go. visibilityAt off-world still says "unseen" — there's no vision out there either. A bot that walks toward whatever it hasn't seen yet will walk at the border forever unless it also checks the ground:

# somewhere new AND somewhere you could stand
if game.visibilityAt(tx, ty) == "unseen" and game.terrainAt(tx, ty) == "normal":
    unit.moveTo(tx, ty)

Note the == "normal" rather than != "mountain". terrainAt can still return "unseen", but only if the server genuinely failed to send that cell's data — never because of fog. Treating that as walkable would be a bug in your bot, so test for what you want, not for what you don't.

There's no way to ask how big the world is, and that's deliberate — you find the edge the same way you'd find a mountain range, by looking. If the world grows later, your bot needs no changes.

08 What's yours vs. what's the engine's

The most important idea in this whole document.

The API is small on purpose. It hides only engine mechanics you couldn't compute yourself — serialization, coordinate projection, pathing, collision, fog-of-war truth. Everything else — finding, sorting, filtering, range checks, target selection, role logic, economy, combat decisions — is yours to write, in your own language.

That's not a limitation. That is the game.

You came to build a bot; the fun is in the deciding. So there is no findClosest, no canGather, no game.hatcheries shortcut. Each is a one-liner you already know how to write:

You might reach for…Write it yourself
unit.findClosest(resources)min(game.resources, key=lambda r: unit.position.distanceTo(r.position))
unit.canGather(r)unit.position.distanceTo(r.position) <= game.gatherRange
game.hatcheries[s for s in game.structures if s.type == "hatchery"]
unit.inventoryFreeunit.inventoryCapacity - sum(unit.inventory.values())
Writing your bot with an LLM? This works in your favour. Every one of these is trivial for an assistant to generate — and because the primitives are shared, no two bots collapse onto the same engine-blessed move. Clear names and predictable shapes are the LLM-friendly part; pre-made decisions are not.

09 A complete starter bot

Harvest → return → deposit. Everything above, wired together. Edit it — it's meant to be replaced.

Python

def play(game):
    hatcheries = [s for s in game.structures if s.type == "hatchery"]
    if not hatcheries:
        return
    home = hatcheries[0]

    # Spawn a basic miner when we can afford one and the slot is free.
    if home.inventory.get("mineral", 0) >= 200:
        home.spawnUnit(["WORK", "CARRY", "MOVE"])

    for unit in game.units:
        free = unit.inventoryCapacity - sum(unit.inventory.values())

        if free > 0 and game.resources:
            # Finding the nearest resource is our craft — not an API helper.
            target = min(game.resources,
                         key=lambda r: unit.position.distanceTo(r.position))
            if unit.position.distanceTo(target.position) <= game.gatherRange:
                unit.gather(target)
            else:
                unit.moveTo(target.position.x, target.position.y)  # re-issued every tick
        else:
            # Full (or nothing to mine): carry it home and deposit.
            if unit.position.distanceTo(home.position) <= game.transferRange:
                unit.transfer(home)
            else:
                unit.moveTo(home.position.x, home.position.y)

JavaScript

function play(game) {
    const hatcheries = game.structures.filter(s => s.type === "hatchery");
    if (!hatcheries.length) return;
    const home = hatcheries[0];

    if ((home.inventory.mineral ?? 0) >= 200)
        home.spawnUnit(["WORK", "CARRY", "MOVE"]);

    for (const unit of game.units) {
        const carried = Object.values(unit.inventory).reduce((a, b) => a + b, 0);
        const free = unit.inventoryCapacity - carried;

        if (free > 0 && game.resources.length) {
            const target = game.resources.reduce((best, r) =>
                unit.position.distanceTo(r.position) < unit.position.distanceTo(best.position) ? r : best);
            if (unit.position.distanceTo(target.position) <= game.gatherRange)
                unit.gather(target);
            else
                unit.moveTo(target.position.x, target.position.y);
        } else {
            if (unit.position.distanceTo(home.position) <= game.transferRange)
                unit.transfer(home);
            else
                unit.moveTo(home.position.x, home.position.y);
        }
    }
}
module.exports = { play };
Ship your entry point right. Python: define play(game) in player.py. JavaScript: module.exports = { play } in player.js. The engine finds and calls it.

10 Languages & the HTTP bridge

The object API above is the canonical surface. The sandbox is built for 24 languages; not every one reaches this API yet — here's the honest state.

LanguageState today
Python, JavaScript, TypeScriptThe full Game / Unit / Structure / Resource / Position object API documented here, via a persistent worker.
The other 21 (Go, Rust, C#, Java, Ruby, C/C++, Lua, Kotlin, …)Docker images and build pipelines exist; each is waiting on its persistent-worker entrypoint. Until it lands, bots in these languages do not run: the older per-tick path they would have used is deliberately switched off, and the server refuses to start if anyone tries to switch it back on.

REST endpoints — /api/v1/player/…

A worker-scoped HTTP surface, authenticated with the rotating worker token. A persistent-worker bot never needs it — its tick message already carries the snapshot and its reply carries the intents — so treat this table as reference. Every response is a { "success": true, "data": … } envelope (or "errorMessage" on failure).

Method & pathBody / query
GET /gameYour whole visible world snapshot.
GET /resourcesBasic resource nodes — position and generated amount. Public by design: the static world is public, the dynamic world is fogged.
GET /cell?x=&y=One cell's terrain + resources.
POST /move{ unitId, x, y }
POST /gather{ unitId, x, y }
POST /attack{ unitId, targetId }
POST /spawn{ x, y, unitType }
POST /spawn-from-hatchery{ hatcheryId, unitType, body: [] }
POST /build-structure{ x, y, structureType }
One wire quirk: on the HTTP /game response the units array is named creeps (not units). The object runtimes hide this; raw HTTP callers should expect it.

Where this comes from

This page describes the runtime object surface as it actually exists: every field and method is checked against the in-container worker entrypoints — the objects a Python or JavaScript bot actually touches — and the HTTP table against the player API controller. It is hand-written for people who write bots, not generated.

Why the surface is this small, and what was deliberately left out, is argued in the engineering write-up.
